1. Project in One Minute

PhisSafe accepts a website URL, extracts measurable characteristics from the URL and website, passes those characteristics to a trained machine-learning model, returns a phishing/legitimate prediction, explains important indicators to the user, and stores scan information for history.

User enters URL

→

→
ML Model
→
Prediction + Explanation
→
Next.js Result
→
Supabase/PostgreSQL
Core principle: The ML model does not directly understand a URL as a human does. The feature-extraction layer converts the website into a structured feature vector. The model learns from the same feature definitions during training and uses them again during live scans.

2. System Architecture

USER | v NEXT.JS FRONTEND | URL submitted v FLASK API | v LIVE FEATURE EXTRACTION |-- URL analysis |-- HTML analysis (BeautifulSoup) |-- DNS checks |-- SSL/TLS checks |-- other agreed indicators | v FEATURE VECTOR | v TRAINED SCIKIT-LEARN MODEL |-- Logistic Regression |-- SVM |-- Random Forest | v PREDICTION + SCORE + IMPORTANT INDICATORS | +------> NEXT.JS RESULT / EXPLAINABILITY UI | +------> SUPABASE / POSTGRESQL |-- authentication |-- users |-- scan history |-- reports / stored results

Frontend — Next.js

Handles what the user sees and interacts with: URL input, scan button, result page, history, dashboards and explanation of the prediction.

API — Flask

Acts as the bridge between the JavaScript/Next.js application and the Python feature-extraction and ML services.

Feature Extraction — Python

Inspects the supplied website and turns useful characteristics into the exact structured inputs expected by the ML model.

ML — Scikit-learn

Learns patterns from labelled phishing/legitimate examples and produces a classification for a new feature vector.

Database/Auth — Supabase + PostgreSQL

Stores user-related data and scan history and supports authentication and relational data management.

Explainability

Converts technical model output into understandable information such as risk score and relevant website indicators. A model prediction should not be presented as an unexplained black box.

4. Development Order — When to Do What

Work should progress in dependency order. Do not wait for every screen to be finished before building the ML and API foundations. The phases below are the recommended execution sequence. If the college provides fixed dates, map those dates onto these phases.

1

Phase 1 — Requirements & Contract Definition

All members together. Agree on the exact feature list, prediction labels, API format, database fields, folder structure, Git branches and definition of done.

  • Confirm prediction classes: e.g. phishing and legitimate.
  • Freeze the first version of the feature list and feature order.
  • Decide which features are static/dataset-based and which are available during live scanning.
  • Decide API request/response JSON format.
  • Decide database tables and fields.
  • Create a shared README and issue/task board.
Gate: No one should independently change the feature names/order or API response structure after this without informing the whole team.
2

Phase 2 — Dataset + Feature Specification

Sana owns ML; Maseera and Rayyan collaborate.

  • Obtain and document the dataset source and licence/usage conditions.
  • Inspect columns, labels, missing values, duplicates and class distribution.
  • Map dataset features to the features that can be calculated during live scanning.
  • Document every feature: name, meaning, type, allowed values and extraction method.
  • Identify features that require DNS, SSL, HTML or external domain information.
3

Phase 3 — ML Baseline & Model Comparison

Sana owns; Fizza evaluates.

  • Clean and preprocess the dataset.
  • Split data into training and test sets without data leakage.
  • Train Logistic Regression, SVM and Random Forest baselines.
  • Evaluate accuracy, precision, recall, F1-score and confusion matrix.
  • Prefer metrics appropriate for phishing detection; recall is important because missed phishing sites are costly.
  • Document the final model-selection decision and its justification.
4

Phase 4 — Live Feature Extraction

Maseera owns; Rayyan refines.

  • Implement URL parsing and agreed URL-based indicators.
  • Implement safe website fetching.
  • Parse HTML using BeautifulSoup.
  • Implement agreed HTML indicators such as forms, links, scripts and external references where appropriate.
  • Implement DNS checks required by the feature specification.
  • Implement SSL/TLS checks required by the feature specification.
  • Return a structured feature object in the exact order/type expected by the model.
Security: A user-supplied URL is untrusted input. Fetching must be controlled and validated. Do not build an endpoint that blindly accesses arbitrary internal/private resources.
5

Phase 5 — Model Packaging

Sana owns; Fizza verifies.

  • Retrain the selected final model on the agreed training data.
  • Save the model and every required preprocessing object.
  • Version the model file.
  • Document the exact feature order and preprocessing pipeline.
  • Verify that a fresh Python process can load the model and predict successfully.
6

Phase 6 — Flask API

Fizza owns; all technical members integrate.

  • Create health/status endpoint.
  • Create scan/prediction endpoint.
  • Validate incoming request data.
  • Call feature extraction.
  • Call the saved ML model.
  • Return a stable JSON response.
  • Handle errors without exposing internal stack traces to users.
  • Test the endpoint independently before connecting the frontend.
7

Phase 7 — Database, Auth & History

Rayyan owns.

  • Set up Supabase project and PostgreSQL schema.
  • Define user/auth relationship.
  • Create scan-history structure.
  • Store URL, result, score, timestamp and only the feature/report fields actually needed.
  • Implement user-specific history access.
  • Define authorization rules so one user cannot read another user's private history.
8

Phase 8 — Frontend Integration & Explainability

Maseera builds pages; Sana integrates ML output; Fizza supports API integration.

  • Create URL scan page.
  • Connect scan form to Flask API.
  • Show loading, success and error states.
  • Display prediction and risk/probability only when the model output supports it.
  • Display understandable indicators/reasons.
  • Display scan history from Supabase.
  • Ensure mobile and desktop layouts are usable.
9

Phase 9 — Full Integration & Testing

All members together. Test the real end-to-end flow, not only individual modules.

  • Enter a valid URL in the UI.
  • Confirm request reaches Flask.
  • Confirm features are extracted correctly.
  • Confirm feature vector matches model contract.
  • Confirm model loads and predicts.
  • Confirm response reaches Next.js.
  • Confirm result is stored correctly.
  • Confirm history displays the correct user's scans.
  • Test invalid URLs, unavailable sites, timeouts and server errors.
10

Phase 10 — Documentation, Demo & Viva

All members, with individual ownership of their section.

  • Freeze the working version before the final demo.
  • Document architecture and data flow.
  • Document dataset and model evaluation.
  • Document API endpoints and database schema.
  • Prepare screenshots and test cases.
  • Each member prepares a clear explanation of their primary and secondary roles.
  • Run the complete demo from a clean environment.

5. Sana — Detailed Execution Guide

Primary Owner

ML Model Engineering

Primary

Goal: Produce a validated, reproducible model that accepts the agreed feature vector and returns a reliable phishing/legitimate prediction.

5.1 Dataset work

  • Find/select the project dataset.
  • Record dataset source, number of rows, columns and label definition.
  • Check missing values, duplicates and suspicious/invalid rows.
  • Check phishing vs legitimate class balance.
  • Separate input features from the target label.

5.2 Preprocessing

  • Decide how missing values are handled.
  • Encode categorical values if present.
  • Scale features where required, especially for algorithms such as SVM and Logistic Regression.
  • Keep preprocessing reproducible and save it together with the model when needed.
  • Avoid data leakage: preprocessing decisions that learn from data must not use the test set.

5.3 Train and compare models

Logistic Regression

Simple classification baseline. Fast and comparatively easy to explain.

SVM

Finds a separating decision boundary and can work well with structured feature data.

Random Forest

Combines multiple decision trees and can capture nonlinear relationships and feature importance.

5.4 Evaluation

Do not report only accuracy. Record at least:

  • Precision: Among sites predicted phishing, how many were actually phishing?
  • Recall: Among actual phishing sites, how many did the model catch?
  • F1-score: Balance between precision and recall.
  • Confusion matrix: Shows correct and incorrect classifications by class.
  • Accuracy: Overall proportion classified correctly; interpret carefully if classes are imbalanced.

5.5 Optimization and final model

  • Choose the best candidate based on the project's evaluation criteria.
  • Tune appropriate hyperparameters.
  • Re-evaluate on held-out data.
  • Record the final model version and parameters.
  • Export model + preprocessing pipeline.
  • Give Fizza a tested model-loading example.

5.6 Secondary — Next.js & Explainability

  • Understand the exact API response fields.
  • Decide what model output can safely be shown to a user.
  • Help design risk/result cards.
  • Map technical indicators to human-readable explanations.
  • Do not call probability a guaranteed certainty.
Your final handoff: Dataset documentation + preprocessing pipeline + model comparison report + selected model + saved model/preprocessor + feature contract + explanation of model output.

7. Maseera — Detailed Execution Guide

Primary Owner

Live Feature Extraction

Primary

Goal: Convert a submitted website into the exact features used by the ML model.

7.1 URL analysis

Implement only features agreed in the shared feature specification. Possible categories include URL length, number of dots/subdomains, suspicious symbols/keywords, IP-address usage and other validated indicators.

7.2 HTML analysis with BeautifulSoup

  • Fetch HTML using controlled timeouts.
  • Parse the HTML with BeautifulSoup.
  • Extract agreed indicators such as forms, links, scripts and external references.
  • Record extraction failures instead of silently producing incorrect values.

7.3 DNS and SSL/TLS checks

  • Perform only the DNS checks defined in the feature contract.
  • Check required HTTPS/certificate properties where technically appropriate.
  • Remember: HTTPS alone does not prove that a site is legitimate.
  • Use timeouts and safe failure behavior.

7.4 Feature-vector contract

The output must be deterministic and match training:

{ "url_length": 38, "has_https": 1, "has_at_symbol": 0, "num_subdomains": 2, "num_forms": 1, "num_external_links": 7 // ...only the agreed features }

The example above is illustrative. The team must replace it with the actual frozen feature set used by the trained model.

7.5 Security requirements

Critical: A URL submitted by a user is untrusted. The live scanner must not blindly fetch arbitrary internal/private addresses or become a server-side request forgery (SSRF) risk. Use URL validation, network restrictions, timeouts, redirect controls and safe error handling appropriate to your environment.

7.6 Secondary — Frontend pages

  • Build scan page.
  • Build history page.
  • Build admin/report pages if required by the project scope.
  • Use the agreed UI design system.
  • Keep API calls separate from presentational components where practical.
Your final handoff: Feature-extraction module + feature documentation + safe scanning behavior + sample feature outputs + frontend pages assigned to you.

9. Integration Contract — Everyone Must Follow This

Most integration failures happen because two members make reasonable but different assumptions. This section prevents that.

9.1 Feature Contract

The team must maintain one authoritative feature specification containing:

  • Feature name
  • Meaning
  • Data type
  • Allowed/range of values
  • How it is calculated
  • Whether it is available during live scanning
  • Its exact position/order in the model input
Rule: Training and live scanning must produce the same feature representation. If the model was trained on 25 features, the live pipeline cannot casually send 24 or 26.

9.2 API Contract

Use one agreed request/response structure. For example:

POST /scan Request { "url": "https://example.com" } Success response { "prediction": "legitimate", "score": 0.03, "indicators": [ { "name": "example indicator", "value": 0, "meaning": "human-readable explanation" } ] } Error response { "error": "Unable to scan the supplied URL" }

This is a template, not a mandatory final schema. Freeze the actual schema before frontend/backend integration.

9.3 Database Contract

Agree on field names before writing frontend queries. At minimum, every scan should be traceable to the correct user and timestamp.

9.4 Git & Collaboration Rules

  • Each member works on a feature branch.
  • Use meaningful commit messages.
  • Pull/rebase or otherwise synchronize before opening a merge request/pull request according to the team's chosen workflow.
  • Do not commit secrets, API keys, database passwords or private credentials.
  • Do not silently modify another member's contract.
  • Before merging, test the affected module.
  • Keep README/setup instructions updated when dependencies or environment variables change.

13. Definition of Done

A task is not "done" merely because code exists. It is done when it is implemented, tested, documented and integrated.

  • Code works locally.
  • Inputs and errors are handled.
  • Relevant tests pass.
  • Another member can run/use the module from the documentation.
  • Inputs/outputs match the shared contract.
  • No secrets are committed.
  • Changes are committed and pushed to the correct branch.
  • Integration with dependent modules has been verified.
  • Known limitations are documented.

14. Critical Rules to Remember

1. Feature consistency: Training-time and live-time features must match exactly.
2. Security: Never blindly fetch arbitrary user-supplied URLs from a server.
3. ML claims: A probability/score is not a guarantee that a website is malicious or safe.
4. HTTPS: HTTPS is useful information, not proof that a website is legitimate.
5. Integration: Freeze API, feature and database contracts before parallel development.
6. Reproducibility: Save preprocessing and model versions together and document how to load them.
7. Ownership: Primary owner leads implementation; secondary owner must understand enough to collaborate and troubleshoot.
8. Demo: Always test the entire URL → features → model → UI → database path before presenting.
