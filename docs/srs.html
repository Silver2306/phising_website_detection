1. Introduction

1.1 Purpose

This document defines the high-level software requirements for a Phishing Website Detection System. The system will allow authenticated users to submit website links and receive an automated prediction indicating whether a website is legitimate or potentially phishing.

The solution will combine machine learning classification with phased analysis of the submitted URL, available domain and SSL information, and safely retrieved HTML content.

1.2 Project Objective

The objective is to create a practical web-based platform that helps users assess website risk before entering personal, financial, or account information. The system will also support user reporting, community voting, administrator review, and maintenance of an internal Verified Phishing List.

1.3 Scope

The initial version will include:

  • Authenticated access for registered users.
  • Single-URL website scanning.
  • Phased hybrid website analysis.
  • Binary machine learning classification.
  • Low, medium, and high risk-level display.
  • Explainable scan results.
  • Personal scan history.
  • Structured reporting and community voting.
  • Administrator review of eligible reports.
  • An internal Verified Phishing List.
Confirmed scope decision: Guest access is excluded from the initial version. Users must register and log in before scanning a website.

2. Overall Description

2.1 Product Perspective

The system will be a web application with a Next.js (App Router) frontend, a Flask-based backend API, a machine learning classification model, and a provisional Supabase PostgreSQL database.

2.2 Detection Approach

The system will use a phased hybrid detection approach. It will not fully execute or interact with webpage JavaScript. Instead, it will perform controlled analysis in stages.

  1. URL analysis: Examine the structure and characteristics of the submitted link.
  2. Domain and SSL analysis: Evaluate available domain, DNS, and certificate information.
  3. Controlled HTML analysis: Retrieve and inspect limited webpage content, including forms, links, and HTML indicators.

The system will not automatically download files or perform full browser-behaviour analysis.

2.3 Classification Output

The deployed model will use binary classification:

  • Legitimate
  • Phishing

The application will additionally display:

  • Phishing probability
  • Low, medium, or high risk level
  • Main warning indicators
  • Completed or failed analysis stages
  • Recommended user action

3. Overall System Flow

User registers or logs in ↓ User enters one website URL ↓ System validates the URL ↓ System checks the internal Verified Phishing List ↓ System performs phased analysis: • URL analysis • Domain and SSL analysis • Controlled HTML analysis ↓ Extracted features are passed to the deployed ML model ↓ Model predicts Legitimate or Phishing ↓ System calculates phishing probability and risk level ↓ Verified-list result and ML result are combined ↓ User receives an explainable result ↓ Complete scan result is stored in the user’s history ↓ User may report the result or vote on an existing report ↓ Eligible reports move to administrator review ↓ Administrator may add the exact URL to the Verified Phishing List

3.1 Scan Processing

Scanning will be synchronous in the initial version. The backend will process the request directly and return a result after completing the required analysis stages.

Reasonable limits will be applied to prevent excessively long or unsafe requests. Detailed technical rules will be defined later.

3.2 Incomplete Analysis

The handling of missing or unavailable features remains open. The current preference is to avoid providing a prediction when required analysis cannot be completed reliably.

4. User Roles

4.1 Registered User

A registered user will be able to:

  • Create an account using email and password.
  • Verify the registered email address.
  • Log in and log out.
  • Reset a forgotten password.
  • Submit one URL at a time for analysis.
  • View explainable scan results.
  • View personal scan history.
  • Submit structured reports.
  • Vote on reported websites.
  • Track the status of submitted reports.

4.2 Administrator

At a high level, an administrator will be able to:

  • Access a protected administrator area.
  • Review reports eligible for administrative review.
  • Review community voting information.
  • Mark reports as verified, rejected, or inconclusive.
  • Add confirmed exact URLs to the Verified Phishing List.
  • View relevant system and scan information.

Detailed administrator permissions are still to be decided.

6. Machine Learning Requirements

6.1 Model Development

The machine learning workflow will include:

  1. Selection of a suitable phishing website dataset.
  2. Data cleaning and preparation.
  3. Selection of features that can also be extracted from newly submitted websites.
  4. Training of multiple classification algorithms.
  5. Comparison of model performance.
  6. Selection and deployment of the best-performing model.

6.2 Model Comparison

Multiple classifiers will be evaluated. The exact algorithms will be finalised later. Likely options include Logistic Regression, Decision Tree, Random Forest, Support Vector Machine, and optionally XGBoost.

6.3 Evaluation Metrics

The project will consider:

  • Accuracy
  • Precision
  • Recall
  • F1-score
  • False-negative rate
  • Prediction time

The final model will not be selected using accuracy alone. Phishing recall and false-negative rate will receive particular attention.

6.4 Feature Consistency

The deployed model shall use only features that can be extracted safely and consistently from newly submitted URLs. The final dataset and feature list remain to be decided after research.

7. Reporting and Community Review

7.1 Structured Reports

Registered users may submit a report for reasons such as:

  • Incorrect prediction
  • Known phishing website
  • Known legitimate website
  • Website behaviour has changed
  • Other concern

7.2 Community Voting

Registered users may vote on reported websites using options such as:

  • Likely Phishing
  • Likely Legitimate

Community voting will support administrative review but will not independently determine the final status.

7.3 Escalation to Administrator

Reports will generally become eligible for administrator review after reaching a configurable voting threshold. The provisional threshold is 20 valid votes.

High-risk or urgent reports may be escalated earlier. The exact escalation rules will be finalised later.

7.4 Report Statuses

Pending Community Review ↓ Eligible for Admin Review ↓ Under Admin Review ↓ Verified / Rejected / Inconclusive

8. Verified Phishing List

The system will maintain an internal list of exact URLs that have been verified as phishing by an administrator.

8.1 Matching Rule

The initial version will use exact URL matching only. Domain-wide and subdomain-wide matching are excluded for now.

8.2 Combined Result Logic

The system will check the Verified Phishing List and still run the machine learning analysis. A verified phishing status will override a conflicting model prediction.

Submitted URL ↓ Check Verified Phishing List + Run ML Analysis ↓ Combine Results ↓ Display Final Status

No external threat-list API will be used in the initial version.

9. Non-Functional Requirements

9.1 Usability

  • The interface shall be clear and understandable to non-technical users.
  • Results shall use simple labels and actionable guidance.
  • The application shall provide clear error and validation messages.

9.2 Performance

  • The system shall process one URL per scan request.
  • The system shall use reasonable request limits and timeouts.
  • The system shall avoid unnecessary full-page execution or file downloads.

9.3 Security

  • The system shall require authentication for all scans.
  • The system shall protect administrator functionality.
  • The backend shall validate submitted URLs.
  • The system shall not execute webpage JavaScript during controlled HTML analysis.
  • The system shall not automatically download files from submitted websites.
  • Detailed security implementation controls will be defined in a later design phase.

9.4 Reliability

  • The system shall record analysis-stage status.
  • The system shall not present a result as guaranteed proof.
  • The system shall handle unreachable or invalid websites gracefully.

9.5 Maintainability

  • The frontend, backend, machine learning, and data layers should remain modular.
  • The deployed model should be replaceable without redesigning the full application.
  • Model versions should be recorded with scan results.

11. High-Level Data Requirements

The system is expected to store data related to:

  • User accounts and profiles
  • Website scan records
  • Scan results and warning indicators
  • Model version used for each prediction
  • User reports
  • Community votes
  • Verified phishing URLs
  • Administrator review outcomes

The detailed database schema, URL-redaction policy, and storage of sensitive query parameters will be decided in the next design phase.

12. Assumptions and Constraints

  • Users will require internet access to use the web application.
  • The initial system will scan one URL at a time.
  • The model will be trained before deployment and will not retrain for every scan.
  • Model training will occur offline during the initial version.
  • No external threat-intelligence API will be used initially.
  • The system will not function as a complete malware sandbox.
  • Some domain, SSL, or HTML information may be unavailable for certain websites.
  • The result will be advisory and not legally or technically definitive.

14. High-Level Acceptance Criteria

The initial system will be considered functionally acceptable when:

  1. A user can register, verify an email address, log in, and reset a password.
  2. An authenticated user can submit one valid website URL.
  3. The system can perform the agreed phased analysis.
  4. The deployed model can classify the submitted website as Legitimate or Phishing.
  5. The user receives a probability, risk level, warning indicators, and safety guidance.
  6. The complete result is stored in the user’s scan history.
  7. The user can submit a report and participate in community voting.
  8. An eligible report can be reviewed by an administrator.
  9. An administrator can add an exact verified phishing URL to the internal list.
  10. The system checks both the Verified Phishing List and the ML model for future scans.
